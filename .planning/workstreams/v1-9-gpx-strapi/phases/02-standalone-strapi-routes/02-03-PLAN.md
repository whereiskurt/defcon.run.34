Close the standalone-route loop on the rendering + delivery side. A standalone CMS route arrives
from the manifest (plan 02-02) with no precomputed `bounds`, so add the client-side bounds fallback
(design §4) so fit-on-toggle still frames it; and verify/enable the cross-origin path (Risk 1) so

separate) — the deliverable is the code/terraform change plus the verified verification.
</objective>

manifest entry carries `m.bounds` (the pre-cache loop that maps `m.bounds` → `[[minLon,minLat],

In the per-route load block inside `add()` — where each route's GPX is already fetched and parsed
(`const file = parseGPX(await gpxRes.text())` then `this.setRouteData(m.fileId, file.toGeoJSON())`)

derive the bounding box from that parsed GeoJSON and store it in `this.routeBounds` in the SAME
`[[minLon,minLat],[maxLon,maxLat]]` shape the existing bounds path uses.

Add a small pure helper (e.g. `boundsFromGeoJSON(fc)`) that walks the FeatureCollection geometry
coordinates (LineString / MultiLineString from `toGeoJSON()` tracks) and returns
`[[minLon,minLat],[maxLon,maxLat]]`, or `null` if there are no coordinates. Guard against an empty
geometry (return without setting bounds — never store a degenerate/NaN box). Keep it defensive:
this runs inside the existing per-route try/catch, so a parse quirk on one route must not break
others.

Do NOT change the line/glow/POI layers, the manifest fetch, or `fitToRoutes()` itself — it already
reads `this.routeBounds`, so populating that map is the whole fix. Keep the change minimal (~5–15
lines incl. the helper).

Primary fix — attach a CORS response-headers policy to that behavior:
- Add an `aws_cloudfront_response_headers_policy` resource (e.g. `cms_media_cors`) with a
  `cors_config` that allows the studio origin: `access_control_allow_origins` = the site's gpx

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Studio browser (`gpx.{zonename}`) → CMS media CloudFront (`cms.{zonename}`) | Cross-origin GET of a public `.gpx` asset; CORS governs whether the studio JS may read the response. |
| CloudFront CORS allow-list → arbitrary web origins | A too-broad allow-list would let any site read CMS media via a user's browser. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-07 | Information Disclosure / Spoofing | CMS media CORS allow-list | low | mitigate | Scope `access_control_allow_origins` to the gpx studio origin (`https://gpx.${var.dns.zonename}`) rather than `*`; methods limited to GET/HEAD/OPTIONS; credentials disabled. CMS media is already public static content, so exposure is limited even if broadened, but the allow-list is kept narrow by default. |
| T-02-08 | Tampering (canvas taint) | Cross-origin GPX fetch in the studio | low | accept | The `.gpx` is fetched as text and parsed (`parseGPX`), never drawn to a canvas, so cross-origin reads need only `Access-Control-Allow-Origin` and raise no canvas-taint issue. Marker-image canvas taint (`map.addImage` from cross-origin) is a separate Phase-3 concern (Risk 3) and out of scope here. |

No package-manager installs in this plan — no supply-chain (T-*-SC) threat applies.
</threat_model>
