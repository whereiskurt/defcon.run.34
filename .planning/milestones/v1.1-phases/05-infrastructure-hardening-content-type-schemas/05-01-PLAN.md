  <name>Task 1: Fix worker Litestream sync script for safe WAL/SHM handling</name>
  <files>apps/run.cms/app/litestream-sync.sh</files>
  <action>
Rewrite the periodic sync loop in `apps/run.cms/app/litestream-sync.sh` to safely handle SQLite WAL/SHM files. The initial restore section (lines 1-36) is fine — only the periodic sync loop (lines 38-61) needs changes.

Replace the current unsafe sync loop with:

1. Restore to an isolated temp directory (NOT alongside the live database):
   ```bash
   TEMP_DIR=$(mktemp -d)
   TEMP_DB="${TEMP_DIR}/strapi.db"
   ```

2. After successful restore, checkpoint the restored database to fold WAL into the main file:
   ```bash
   sqlite3 "$TEMP_DB" "PRAGMA wal_checkpoint(TRUNCATE);"
   ```

3. Remove any WAL/SHM files from the restored database (should be clean after checkpoint):
   ```bash
   rm -f "${TEMP_DB}-wal" "${TEMP_DB}-shm"
   ```

4. Stop Strapi briefly via supervisorctl for a safe file swap:
   ```bash
   supervisorctl stop strapi 2>/dev/null
   ```

5. Remove all three old database files to prevent stale WAL application:
   ```bash
   rm -f "${DB_PATH}-wal" "${DB_PATH}-shm"
   ```

6. Move the checkpointed database into place:
   ```bash
   mv "$TEMP_DB" "$DB_PATH"
   ```

7. Restart Strapi:
   ```bash
   supervisorctl start strapi 2>/dev/null
   ```

8. Clean up the temp directory in all cases (success and failure):
   ```bash
   rm -rf "$TEMP_DIR"
   ```

The initial restore section should also be updated to checkpoint after restore — add a `sqlite3 "$DB_PATH" "PRAGMA wal_checkpoint(TRUNCATE);"` and `rm -f "${DB_PATH}-wal" "${DB_PATH}-shm"` after the successful initial restore (before setting the ready flag), to ensure a clean starting state.

Keep the existing header, env vars, and script structure. Do NOT change LITESTREAM, CONFIG, DB_PATH, DB_DIR, READY_FLAG, or SYNC_INTERVAL variables.

**Step A: Update plugins.ts S3 config to v5 format**

In `apps/run.cms/app/config/plugins.ts`, restructure the `uploadConfig` section. The existing env var lookups (s3AccessKey, s3Bucket, regionShort, siteDomain, cdnBaseUrl, s3RootPath) remain unchanged. Only the config object structure changes:

1. Change `provider` from `'@strapi/provider-upload-aws-s3'` to `'aws-s3'` (Strapi 5 short name)

2. Restructure `providerOptions` from flat format to nested v5 format:
   - `baseUrl` and `rootPath` stay at the `providerOptions` level
   - Create new `s3Options` object inside `providerOptions`
   - Move `accessKeyId` and `secretAccessKey` into `s3Options.credentials`
   - Move `region` into `s3Options`
   - Move `params` (Bucket, ACL) into `s3Options`

The resulting structure must be:
```typescript
{
  config: {
    provider: 'aws-s3',
    providerOptions: {
      baseUrl: cdnBaseUrl,
      rootPath: s3RootPath,
      s3Options: {
        credentials: {
          accessKeyId: s3AccessKey,
          secretAccessKey: env('S3_MEDIA_SECRET_KEY'),
        },
        region: env('S3_MEDIA_REGION', 'us-east-1'),
        params: {
          Bucket: s3Bucket,
          ACL: null,
        },
      },
    },
    actionOptions: {
      upload: {},
      uploadStream: {},
      delete: {},
    },
  },
}
```

Do NOT change the email, users-permissions, or strapi-plugin-sso config sections. Do NOT change the env var names or the conditional `s3AccessKey && s3Bucket` check. Preserve existing comments about CDN URL construction and rootPath pattern.
