## Facts resolved live during planning — do not re-derive, do not plan discovery for these

Verified 2026-07-30 against the real bucket. These close the open questions PATTERNS.md
raised about credentials and CONTEXT.md raised about dead keys.

1. **Cross-account read works with `AWS_PROFILE=dc34-application`.** That profile lists and
   reads `s3://defcon.run.33.backup/AWSDynamoDB/01755225714347-c2695bcb/` successfully.
   `sudo-management` and `dc34-management` both get AccessDenied (no resource policy) — do
   not try them. CONTEXT.md's warning about dead IAM keys refers to the DC33 *repo's own*
   `.env`, which is irrelevant here.
   This is the one place where the profile mechanism and the explicit-env-keys mechanism
   coexist. PATTERNS.md §5 correctly reports that ops scripts in this repo take explicit
   `S3_UPLOADS_*` keys, and that stays true for the WRITE. The READ targets a different
   account where no such key pair exists, so it uses a named profile. Both clients live in
   this one script and they are not interchangeable.

2. **Authoritative export manifest** (`manifest-summary.json`, read live):
   - `exportTime` / `startTime` = `2025-08-15T02:41:54.347Z` — the honest `generatedAt`.
     (Local-time directory listings show 2025-08-14 22:4x EDT; the UTC value is canonical
     and CONTEXT's "2025-08-15" refers to the same object.)
   - `itemCount` 730, `outputFormat` `DYNAMODB_JSON`,
     `tableArn` `arn:aws:dynamodb:us-east-1:427284555693:table/electro-use1-run-defcon-run`.
   - `manifest-files.json` is JSON-lines, one object per data file carrying a
     `dataFileS3Key`. Read it; do not hardcode the four gz filenames.

3. **Item shape, sampled live from `data/lgxsjwpe2e2lxcqauidq623onu.json.gz`** (168 items):
   - Each line is an object with a single `Item` key holding DynamoDB-JSON attributes.
   - The ElectroDB discriminator is `__edb_e__` and the accomplishment value is the PLURAL
     `Accomplishments`. A filter written against the singular matches zero rows and yields
     a silently empty artifact.
   - Attributes present: `pk, sk, gsi1pk, gsi1sk, gsi2pk, gsi2sk, metadata, __edb_e__,
     __edb_v__, createdAt, completedAt, updatedAt, name, description, accomplishmentId,
     userId, year, type`.
   - `year` is a DynamoDB `N`. In that one file the distribution is
     2021:1, 2022:1, 2023:2, 2024:11, **2025:85** — so a year filter is REQUIRED or the
     "DC33" artifact silently smuggles in four other cons.
   - `type` is `S` with values `activity` / `social` / `meshctf`; only `activity` rows carry
     geometry.
   - Geometry lives at `metadata.M.summary_polyline.S`. In that file 46 of 100
     accomplishments had one, and **4 of those 46 were JSON coordinate arrays** rather than
     encoded polylines — both branches are real and both must work.
   - The year-2025 rows with geometry span `2025-08-05` … `2025-08-12`, the DC33 con window,
     which is a useful sanity check on the filter.
   - 31 of that file's rows were year-2025 with non-empty geometry. Across all four files
     (168+139+200+223 = 730 items) the expected final run count is roughly 100-200.

4. **DC33 = year 2025.** DC33's own `api/heatmap/route.ts:208` derives
   `defconNumber = year - 1992`, so 2025 maps to DC33.

5. **The write key is `uploads/HEATMAP/dc33.json`**, produced by `heatmapArtifactKey('dc33')`.
   The run-gpx S3 IAM user is prefix-scoped to `${bucket}/uploads/*`
   (`infra/terraform/modules/s3-uploads/v1.0.0/iam.tf` lines 43, 60, 71, 80, 89, with
   `full_bucket_access = false` at `live/site/services/run.gpx/service.hcl:279`). A
   top-level `heatmap/` key would AccessDeny at runtime.

6. **Local one-off, not a Lambda** (Claude's Discretion, decided): `npx tsx`, gated behind an
   explicit `--apply` flag. The export is frozen and will never change; a scheduled path
   would be permanent cost for a permanently identical result.

    **A. `scripts/backfill-dc33-heatmap.ts`** — invoked as
    `npx tsx scripts/backfill-dc33-heatmap.ts [--apply]` from `apps/run.gpx/webapp`.

    Header doc comment in the shape of `import-dc33.ts:1-16`. It must state: what this
    produces; that the DC33 export is frozen so this is a ONE-OFF; the exact invocation with
    every env var and the `DC33_AWS_PROFILE` default; that the READ is cross-account by
    named profile while the WRITE uses the app's own prefix-scoped keys; that DC33 is
    accomplishment `year` 2025 because DC33's route derives the con number as `year - 1992`;
    and that the entity discriminator value is the plural form.

    Constants at the top: source bucket `defcon.run.33.backup`, source prefix
    `AWSDynamoDB/01755225714347-c2695bcb/`, `DC33_YEAR = "2025"`,
    `DC33_ENTITY = "Accomplishments"`, `DC33_TYPE = "activity"`.

    Two S3 clients, clearly named and commented:
    - `sourceS3` — an `S3Client` for `us-east-1` whose credentials come from
      `fromIni({ profile: process.env.DC33_AWS_PROFILE ?? "dc34-application" })`, importing
      `fromIni` from `@aws-sdk/credential-provider-ini` (already in `package.json`; no install).
    - the app's exported `s3Client` for the write. Do not build a third client and never
      route the write through `sourceS3`.

    Pipeline:
    1. `GetObject` `manifest-summary.json` from the source prefix; parse; take `exportTime`.
       Fail loudly if it is absent — `generatedAt` must be honest and there is no acceptable
       fallback.
    2. `GetObject` `manifest-files.json`; parse it as JSON-lines; collect every
       `dataFileS3Key`. Do not hardcode filenames.
    3. For each data file: `GetObject`, collect the body into a Buffer, `gunzipSync` with
       `node:zlib`, split on newline, `JSON.parse` each non-empty line inside a try/catch
       that counts and skips malformed lines rather than aborting the run.
    4. Select rows where the `__edb_e__` string equals `DC33_ENTITY`, the `year` number
       string equals `DC33_YEAR`, the `type` string equals `DC33_TYPE`, and
       `metadata.M.summary_polyline.S` is a non-empty string.
    5. Dedup on `metadata.M.stravaActivityId.S` when present and non-empty, else on
       `accomplishmentId.S`. Sort the candidate keys before reducing so two runs produce
       byte-identical output.
    6. Geometry: `decodeTrack(summary_polyline)` then `normalizeTrack`. Drop anything under
       two coordinates and count the drops.
    7. `assembleHeatmapArtifact('dc33', exportTime, tracks)` then
       `assertNonAttributable(artifact)`. Do NOT wrap the guard in a try/catch — if it
       throws, the run must die.
    8. Print a `[heatmap-dc33]` summary: files read, lines parsed, malformed lines skipped,
       accomplishments matched, geometry decoded, JSON-array-form count vs encoded-form
       count, deduped, final `runCount` and `totalKm`. Print NO user ids, NO accomplishment
       ids, NO polyline text.

       Then print, as the LAST three lines of output, each alone on its own line with no
       prefix, no padding and no surrounding punctuation:

       - `HEATMAP_DC33_RUNCOUNT=<integer>`
       - `HEATMAP_DC33_TOTALKM=<number>`
       - `HEATMAP_DC33_GENERATEDAT=<iso8601>`

       These are a machine-readable contract, not decoration. 71-08's production probe reads
       `HEATMAP_DC33_RUNCOUNT` out of `71-04-SUMMARY.md` to check the LIVE artifact against
       the number this run actually produced, and it is required to FAIL — not skip — when
       the line is missing or unparseable. Emit them with an exact `KEY=VALUE` shape, one per
       line, so a regex anchored to `^HEATMAP_DC33_RUNCOUNT=(\d+)$` matches. Do not localise
       the numbers, do not thousands-separate them, and do not wrap them in backticks when
       transcribing them into the summary.
    9. Without `--apply`: write the serialized artifact to `./dc33-heatmap.local.json`
       (relative to `apps/run.gpx/webapp`) and print the path.
    10. With `--apply`: additionally send a `PutObjectCommand` to `Bucket: BUCKET`,
        `Key: heatmapArtifactKey('dc33')`, `ContentType: "application/json"`, then re-`GetObject`
        that key, re-parse, and run `assertNonAttributable` on the round-tripped value.
        Print the byte length.

    Exit non-zero on any unhandled failure, on a guard throw, and on a zero-feature result —
    a DC33 artifact with no runs is a bug, not an empty set.

    **B. `scripts/verify-heatmap-artifact.mjs`** — a small dependency-free Node script taking
    one argument, either a local file path or a URL. It loads the JSON (reading the file or
    fetching the URL) and asserts, printing one line per check and exiting non-zero on the
    first failure:
    - the root has exactly the keys `type`, `meta`, `features`, and `type` is `FeatureCollection`;
    - `meta` has exactly `year`, `generatedAt`, `runCount`, `totalKm`;
    - `meta.runCount` equals `features.length` and is greater than zero;
    - every feature has exactly the keys `type`, `properties`, `geometry`;
    - every feature's `properties` has zero own keys;
    - every geometry is a `LineString` whose `coordinates` is an array of at least two
      two-number pairs within valid lon/lat ranges;
    - the raw serialized text contains none of the substrings `userId`, `accomplishmentId`,
      `stravaActivityId`, `fileId`, `summary_polyline`, `conDay`, or an at-sign — a blunt
      byte-level attribution sweep that does not trust the structural walk;
    - it prints a final line with year, runCount and totalKm.
    This script is deliberately separate from the backfill so 71-08 can point it at the LIVE
    production URL for both years.

    **C. `.gitignore`** — ensure `dc33-heatmap.local.json` is ignored under
    `apps/run.gpx/webapp`. The dry-run artifact must never be committed.
