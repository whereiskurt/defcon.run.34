## Design decisions this plan locks

**New module, not a second unit of the existing one.** `strava-sync-scheduler/v1.1.0/main.tf:15`
hardcodes `function_name = "strava-sync-${var.region.label}"`, so a second live unit of that
module would collide on every resource name. The two alternatives were: generalise the
module behind a `function_basename` variable in a new v1.2.0, or copy it. Copying wins here —
the strava unit is applied and live, and a copy has zero blast radius on it, whereas a
shared module means every future heat-map change re-plans a live Strava Lambda. The copy is
~200 lines of Terraform with one changed local, which is the boring option AGENTS.md asks
for.

**Schedule (Claude's Discretion, decided):** two entries in the `schedules` map, both in
`America/Los_Angeles`:
- `hourly = "cron(0 * 5-10 8 ? 2026)"` — top of every hour on 5-10 August 2026, the DC34 run
  window from `apps/run.gpx/webapp/src/lib/con-days.ts`.
- `daily = "cron(0 4 * * ? *)"` — 04:00 PT every day, year-round. Without this the artifact
  would be stale (or missing) for everyone testing before the con and everyone browsing
  after it, and the whole feature would look broken outside a six-day window.

**The Lambda stays a thin invoker.** PATTERNS.md §4 is right: `lambda/index.mjs` reads one
SSM SecureString and POSTs a URL, with no npm dependency and no bundling. All DynamoDB and
S3 work happens on the run.gpx ECS task role, which already holds those grants. Do not give
this Lambda data-plane permissions.

**Deploy path.** Per AGENTS.md, nothing is applied from a workstation. Validation is
`terragrunt-plan.yml` with `region=us-east-1`, `modules=heatmap-scheduler`; the apply is
`terragrunt-apply.yml` with the same scoping and happens in 71-08.

| Boundary | Description |
