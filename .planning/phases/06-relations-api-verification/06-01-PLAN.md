<research_key_findings>
CRITICAL: inversedBy/mappedBy pairing rules

One side MUST use `inversedBy` (owning side), the other MUST use `mappedBy` (inverse side). If both use `inversedBy`, Strapi creates TWO join tables and data written from one side is invisible from the other. This is the #1 pitfall for Strapi many-to-many relations.

Ownership assignment for this phase:
- Event.routes uses `inversedBy: "events"` → Event is OWNER of Event↔Route
- Route.events uses `mappedBy: "routes"` → Route is INVERSE of Event↔Route
- Route.pointsOfInterest uses `inversedBy: "routes"` → Route is OWNER of Route↔POI
- POI.routes uses `mappedBy: "pointsOfInterest"` → POI is INVERSE of Route↔POI

Target UID format: `api::{singularName}.{singularName}` (e.g., `api::point-of-interest.point-of-interest`)

Bootstrap permission pattern: Use Strapi plugin store with a dedicated key to ensure idempotency. Query for Public role, then upsert find/findOne permissions for each content type.
</research_key_findings>

**Step A: Add the `ensurePublicPermissions` helper function**

Add this function BEFORE the `export default` block (at the top of the file, after any imports):

```typescript
async function ensurePublicPermissions(strapi) {
  const pluginStore = strapi.store({
    type: 'plugin',
    name: 'users-permissions',
  });

  const publicPermissionsConfigured = await pluginStore.get({
    key: 'publicPermissionsConfigured',
  });

  if (publicPermissionsConfigured) {
    return; // Already configured — idempotent guard
  }

  // Find the Public role
  const publicRole = await strapi
    .query('plugin::users-permissions.role')
    .findOne({ where: { type: 'public' } });

  if (!publicRole) {
    strapi.log.warn('[Bootstrap] Public role not found — skipping permission setup');
    return;
  }

  // Grant read-only access (find + findOne) for all three content types
  const publicActions = [
    'api::event.event.find',
    'api::event.event.findOne',
    'api::route.route.find',
    'api::route.route.findOne',
    'api::point-of-interest.point-of-interest.find',
    'api::point-of-interest.point-of-interest.findOne',
  ];

  for (const action of publicActions) {
    const existing = await strapi
      .query('plugin::users-permissions.permission')
      .findOne({ where: { action, role: publicRole.id } });

    if (existing) {
      // Permission record exists — ensure it's enabled
      if (!existing.enabled) {
        await strapi.query('plugin::users-permissions.permission').update({
          where: { id: existing.id },
          data: { enabled: true },
        });
      }
    } else {
      // Permission record doesn't exist — create it
      await strapi.query('plugin::users-permissions.permission').create({
        data: { action, role: publicRole.id, enabled: true },
      });
    }
  }

  // Mark as configured so this doesn't re-run on every restart
  await pluginStore.set({
    key: 'publicPermissionsConfigured',
    value: true,
  });

  strapi.log.info('[Bootstrap] Public API permissions configured (find + findOne for events, routes, points-of-interest)');
}
```

**Step B: Call the helper from the bootstrap function**

Inside the existing `async bootstrap({ strapi })` function, add the public permissions call AFTER the admin user seeding try/catch block (at the end of bootstrap, before the closing brace):

```typescript
    // Configure public read-only API permissions (idempotent)
    try {
      await ensurePublicPermissions(strapi);
    } catch (err) {
      strapi.log.error('[Bootstrap] Failed to configure public permissions:', err);
    }
```

**Key design decisions:**
- Idempotent via plugin store key `publicPermissionsConfigured` — runs once, never re-runs
- Uses Strapi query API (not service API) — directly operates on permission records
- Wrapped in try/catch — permission failure doesn't crash Strapi startup
- Only grants `find` and `findOne` — no create/update/delete (admin-only)
- Runs on both master and worker modes — workers need the same permissions for their local API
