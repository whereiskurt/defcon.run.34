<objective>
Ship the hardening to production and prove each closed defect on the production wire with a
recorded pre/post contrast (MQFX-05), and confirm MQFX-06 is already satisfied without
re-implementing it.

The deploy always runs in GitHub Actions. Local tooling builds and pushes images; `buildpub.yml`
owns the VERSION bump and the immutable ECR tag; `deploy.yml` applies ECS. Never run
`terragrunt apply` locally and never pass `--with-terragrunt` to a release.

Purpose: turn "the tests pass" into "the fixes are demonstrably live and the fleet is
uninterrupted".
Output: a committed probe script, a pre-deploy baseline, a released and deployed image, and a
per-defect evidence table with the counters and continuity assertions the ROADMAP names.

**Hard safety rule.** MQFX-01 (the nil-cipher panic) must NEVER be probed against production —
one crafted PUBLISH carrying a decoded, unencrypted text-message envelope would drop every
connected radio. Its production evidence is negative (no panic, no SIGSEGV, no restart) and its
positive proof lives in 69-01's tests. No probe subcommand may construct such a packet.

**Attribution landmines proven in Phase 68, all of which cost real time.**
1. During an ECS rolling replace BOTH images write to the SAME log group. Attribute every count
   with `--log-stream-names` (per task), never by wall clock.
2. `aws ecs wait services-stable` is NOT a drain gate — it has twice returned while the old task
   was still serving every long-lived MQTT TCP connection. Poll the OLD task to `STOPPED` before
   attributing anything to the new image.
3. `describe-log-streams` can report a `lastEventTimestamp` hours stale on an actively-logging
   stream. Use `get-log-events`.
4. `rollback.yml` does not list `run.mqtt` as an app, so rollback means redeploying the previous
   tag through `deploy.yml`.
5. A probe's log poll must wait for the SPECIFIC substring it needs; waiting on any client-id
   match returns early on the CONNECT line and reports a later decision line as missing.

**Baseline ordering (from 68-08).** The probe script must be COMMITTED before the release runs,
so the pre-deploy baseline is provably produced by the same bytes as the post-deploy run.
Phase 68-05's probes were scratch files that were deleted, which is why its evidence cannot be
re-derived today.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| probe process → production proxy and live mesh | a probe writes real frames to a production listener and can inject packets that reach real radios |
| CI workflow → production ECS and CloudFront | the only sanctioned path to change what serves production |
| CloudWatch log group → the verifier's conclusions | two images write to one group during a rolling replace, so an unscoped query produces confidently wrong attribution |
| operator environment → MQTT credentials and channel keys | secrets needed by the probes must not reach stdout, the repository or the summary |
