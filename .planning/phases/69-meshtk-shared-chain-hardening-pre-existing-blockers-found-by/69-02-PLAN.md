<objective>
Complete MQFX-01's third layer: a per-connection `recover()` so no single frame can ever take
the whole fleet down again. `68-REVIEW.md` CR-01 established that there is no `recover()`
anywhere in the proxy path (`grep -rn "recover()"` across `internal/app`, `internal/credcache`
and `pkg` finds only `internal/app/fleet/otpsend.go` and two test files), so any panic in a
connection goroutine is a process kill that drops every connected radio.

Layers 1 and 2 (the nil-cipher guards) landed in 69-01. This plan is the defense-in-depth
layer: it must hold for the NEXT nil dereference nobody has found yet, which is the whole
point of it being independent of the specific bug.

Purpose: convert "one crafted frame kills the fleet" into "one crafted frame kills one
connection, loudly".
Output: recovery at every per-connection goroutine entry plus a test that proves a panicking
decider takes down one connection and not the process.

branch 69-01 created. Never `apps/run.mqtt/meshtk`; never `internal/embedded/`.

**Serialization.** Wave 2 because every code plan shares one upstream working tree — see
69-01's objective. It does not depend on 69-01's CONTENT, only on its tree not being
concurrently edited.

    Add one small helper in `proxy.go` — name it `recoverConn` — that takes a label, an
    optional `net.Conn` and performs the recover-log-close sequence: recover, and when the
    recovered value is non-nil log through `n.Config.Log.Errorf` with the label, the
    connection's remote address (guarding a nil conn), the panic value, and a
    `runtime/debug` `Stack()`. Close the connection when one was passed. Use a single

    count it; state in the comment that the stack goes through `Config.Log` (logrus
    `TextFormatter`, which quotes) and NOT through `InspectorLogger` (`SimpleFormatter`, no
    quoting), because a multi-line value there would forge log lines.

    Install it as a deferred call at the entry of all four per-connection goroutines:
    `handleProxy` and `handleBackend` in `proxy.go`, `handleProxyV5` and `handleBackendV5` in
    `proxy_v5.go`. In `handleProxy` the new defer must be registered so it runs and still
    lets the pre-existing cleanup closure (ConnTrack delete plus `conn.Close()`) do its work —
    read the existing defer before choosing the order, and do not duplicate the ConnTrack
    delete. In the two downlink loops the recover must also end the loop, which a deferred
    recover does by construction since the panic already unwound it.

    Add the outermost backstop in `cmd.go`: the `StartProxyServer` accept goroutine wraps
    `n.handleProxy(c)` with the same deferred recover, so anything the handler spawns that
    escapes its own recover still cannot reach the top of the process. Do the same for
    `StartProtobufServer`'s `handleProtobuf` spawn — same class, one line, and it is on the
    same process.

    Do not add a recover inside the frame loops themselves (per iteration): the contract is
    per CONNECTION, and swallowing a panic mid-loop would continue serving a connection whose
    invariants just broke. State that choice in the helper's doc comment.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| one connection's goroutine → the proxy process | a single process serves the whole fleet; any unrecovered panic in a connection goroutine is a fleet-wide outage |
| untrusted MQTT client → the rules engine and both codecs | the client chooses every byte that reaches the parse and inspect path, including combinations no test covers |
| recovered panic value and stack → the security log file rotated to S3 | a panic value can embed client-controlled bytes, including newlines |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-69-02-01 | Denial of Service | any panic in `handleProxy` / `handleProxyV5` / `handleBackend` / `handleBackendV5` kills the process and drops every connected radio | critical | mitigate | Task 1 defers `recoverConn` at all four goroutine entries plus both accept-loop spawns; Task 2 proves containment on both codecs and in the downlink direction |
| T-69-02-02 | Repudiation | a silently recovered panic is indistinguishable from a normal disconnect, so the underlying bug is never found | medium | mitigate | `action=PANIC_RECOVERED` with remote address, panic value and a `runtime/debug` stack; Task 2 asserts on that exact line rather than on the call returning |
| T-69-02-03 | Repudiation | a client-controlled panic value or a multi-line stack forging log lines | medium | mitigate | the recovered line is written through `Config.Log` (logrus `TextFormatter`, which quotes), never through the `SimpleFormatter`-backed `InspectorLogger` that WR-05 shows is forgeable; stated in the helper's doc comment |
| T-69-02-04 | Denial of Service | recover masks a real bug into a fast reconnect loop that burns CPU and log volume | medium | accept | recovery is strictly per connection and always closes the socket, so a looping client is visible as repeated `action=PANIC_RECOVERED` lines with the same remote address; the stack keeps the bug diagnosable |
| T-69-02-05 | Denial of Service | a per-iteration recover would keep serving a connection whose invariants just broke | medium | mitigate | deliberately NOT done — the contract is per connection; recorded in the helper's doc comment and enforced by the absence of a recover inside the frame loops |
| T-69-02-06 | Tampering | touching `proxy.go` perturbs the 3.1.1 forwarded bytes | high | mitigate | `proxy_v4_golden_test.go` byte-unedited (git diff empty) and green; a deferred recover writes no wire byte |
| T-69-02-SC | Tampering | dependency substitution via a package-manager install | high | mitigate | nothing is installed; `runtime/debug` is standard library; `git diff --stat origin/main -- go.mod go.sum vendor/` must print nothing |
</threat_model>
