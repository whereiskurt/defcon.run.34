  <name>Task 1: Human-verify ADMN-01..ADMN-03 end-to-end against a live CMS build</name>
  <action>Boot the CMS locally, then walk the three ADMN success criteria against a real build per the steps below — menu link + region-prefixed route resolution (D-01), grid + namespace filter + inline edit + add-row, and the atomic bulk upsert including duplicate rejection and the copy.json S3 export. This is a blocking human checkpoint — the operator confirms each criterion (or lists gaps) before the phase closes.</action>
  <what-built>
    A custom "Copy Catalog" Strapi admin page (src/admin/pages/CopyCatalog.tsx + a register()/addMenuLink hook in src/admin/app.tsx) that lists the full ui-string catalog as a three-column Label · Locale · Value grid with a client-side namespace filter, inline edit, and add-row — plus a POST /ui-strings/bulk-upsert endpoint (route + controller + service on api::ui-string) that upserts dirty + new rows all-or-nothing, reusing the Phase-35 (key,locale) uniqueness guard and the copy.json S3 export.
  </what-built>
  <how-to-verify>
    1. Boot the CMS locally: from `apps/run.cms/app`, run `PORT=1337 npm run develop`. Wait for Strapi to be ready.
    2. Open the admin at http://localhost:1337/admin and sign in. Confirm a **Copy Catalog** link appears in the left nav, and clicking it opens the page (route `/admin/copy-catalog` resolves on localhost — no region prefix). If a region-prefixed environment is available, also confirm the link resolves under `/{region}/admin/copy-catalog` (the D-01 empirical check for the Vite base prefix).
    3. Confirm the grid loads the full catalog as three columns **Label · Locale · Value**, with a Loader shown briefly while it fetches. (If the catalog is empty, confirm the empty-state copy renders.)
    4. **Namespace filter (ADMN-02):** select `bib` → only `bib.*` rows show; select `All namespaces` → every row returns. The filter is instant (no network round-trip).
    5. **Inline edit + upsert (ADMN-03):** change an existing row's Value → the row shows the dirty indicator and Save enables → click **Save** → success toast appears. Reload the page → the edited value persisted and it is the SAME row (an in-place update, NOT a new duplicate).
    6. **Add row (ADMN-01, D-05):** with `bib` filtered, click **Add row** → the new row's Label pre-fills `bib.`; type a unique tail + a Value → **Save** → the new row persists and (via the grid) shows a real id.
    7. **Atomic reject (ADMN-03, D-03):** create a row whose `(key, locale)` already exists (or two new rows sharing one `(key, locale)`) → **Save** → the whole save is rejected: the reject banner + per-row danger cells/inline errors appear and dirty state is preserved. Reload → confirm NOTHING was written (no new or changed rows). Also try a key with an invalid namespace prefix (e.g. `zzz.foo`) → per-row bad-namespace error, nothing written.
    8. **S3 export (FALL-01 reuse):** on a successful save with `CMS_MODE=master` and S3 env present, confirm the `[copy-export] wrote {region}/cms/copy.json` log line fires (or the S3 object updates). Locally without S3 env, confirm it is a logged no-op (expected — never an error).
    9. Confirm the read-only surface is untouched: the bulk-upsert endpoint is admin-authed (an unauthenticated or read-only-token POST to `/ui-strings/bulk-upsert` is denied).
  </how-to-verify>
  <resume-signal>Type "approved" if all three ADMN criteria hold (menu + route resolve, filter + grid + add-row, atomic bulk upsert with duplicate rejection and S3 export), or describe the gaps for a fix pass.</resume-signal>
