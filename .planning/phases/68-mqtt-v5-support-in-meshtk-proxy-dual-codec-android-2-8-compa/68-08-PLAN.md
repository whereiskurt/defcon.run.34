## How the image actually gets its meshtk source (read before syncing)

`apps/build.sh resolve_meshtk` in CI does NOT use a submodule or a pin. It clones
`https://github.com/whereiskurt/meshtk.git` at depth 1 — i.e. whatever `main` is at build time —
and then untars every monorepo-tracked file under `apps/run.mqtt/meshtk/` **on top of** that clone.
Two consequences that decide this plan:

1. Upstream must be merged to `main` BEFORE buildpub runs, or the build picks up the old code.
2. Any overlay-tracked file that upstream changed must be re-synced, or the stale monorepo copy
   silently overwrites the fresh upstream version. `origin/main` currently tracks 21 files under
   `apps/run.mqtt/meshtk/internal/app/server/`, including `proxy_v5.go` and `inspect_v5.go`, so the
   whole server package is mirrored and must stay mirrored.

- **`internal/embedded/gpx/embedded.go` is monorepo-authoritative.** It has been clobbered by a
  vendor-sync before. It must be absent from the PR diffstat.
- **`aws ecs wait services-stable` is not a drain gate.** It returns while the old task still
  serves every long-lived MQTT connection. Poll the old task to `STOPPED` before attributing any
  probe result or log line to the new image.
- **Attribute post-deploy log evidence by log STREAM, never by wall clock.** Both images write to
  the same log group during a rolling replace.

- **`rollback.yml` does not list `run.mqtt`** in its app choices; a rollback would need a different
  mechanism. Know this before starting, not during.
- **Deploy only via GitHub Actions.** No local `terragrunt apply`, ever.
