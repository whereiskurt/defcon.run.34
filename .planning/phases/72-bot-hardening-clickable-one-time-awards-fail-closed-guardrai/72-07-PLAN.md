<objective>
Bound the blast radius of a crowd, and make a fail-closed guardrail degrade visibly
instead of mysteriously.

The lyric cooldown at `cmd.go:583` is per-REQUESTER (10 minutes), so N distinct radios
start N concurrent songs, each its own goroutine, with no global cap. Per-radio load is
unchanged at roughly one message every 3.6 seconds, but the exposure is RF-only
listeners: at 50 talkers the aggregate is ~13.8 messages per second of 200-character
packets, which collapses a LoRa channel long before the server notices.

Separately, 72-04 flips the guardrail failmode to closed. Today BOTH guard sites already
answer with the canned refusal — the design's "silent drop" framing is inaccurate. What
is actually missing is the ability to tell a genuine policy block apart from a sidecar
outage, so a player currently cannot distinguish "the bot refused you" from "the checker
is down".

Purpose: cap the fan-out, and make an outage legible to both the player and the operator.
Output: a global semaphore, an over-cap reply, an outage-aware refusal selector, and a
marker token for the CloudWatch alarm.
</objective>

env override with the documented default. Size it at construction time, not per call, so

mark. That order matters: marking first and refusing second would lock a requester out
for ten minutes while giving them no song at all. On refusal, reply on the PLAIN path
with a short in-character stage-is-full line and return immediately.

return, and a defer at the top of the playback goroutine so both normal completion and
the termination-timer return are covered.

Record the arithmetic in a comment so the number is not mistaken for arbitrary: twelve
concurrent performances of 58 messages over roughly 214 seconds bounds aggregate output
