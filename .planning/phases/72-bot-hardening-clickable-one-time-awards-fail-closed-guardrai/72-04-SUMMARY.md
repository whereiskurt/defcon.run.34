# Phase 72 Plan 04: Guardrail Fail-Closed + Fallback Secret + Outage Alarm Summary

Flipped the mesh ghosts to fail-closed guardrails, plumbed the ricky mint-failure fallback
secret, and added the CloudWatch alarm that makes a sidecar outage visible — **authored
only, nothing applied.**

## What Was Built

### 1. Fail-closed flip (`services/run.mqtt/service.hcl`)

`MESHTK_GUARDRAIL_FAILMODE` on the `run-mqtt-ghosts` container is now `closed`. meshtk's
guard treats any transport error, non-200 status or decode failure from the sidecar as a
BLOCK instead of an allow. Prod is currently `open` (task def `run-mqtt-use1-dc34:122`);
this file is the input that changes it, on the 72-09 apply.

`MESHTK_RICKY_FALLBACK_URL` added to the container's `secrets` block, pointing at
`/{{SITE_LABEL}}/secrets/{{REGION_LABEL}}/mqtt/ricky-fallback-url`. The ordering warning
(ECS refuses to start a task whose `valueFrom` parameter does not exist) is recorded
in-file next to the entry.

### 2. Secret key declaration (`site.hcl`, `.secrets.sops.json.template`)

`ricky-fallback-url` appended to the `mqtt` secret group's `keys` list — that is what
provisions the SSM parameter the new `valueFrom` reads. SOPS template gained
`"ricky-fallback-url": "CHANGEME-ricky-fallback-claim-url"`. **No real value anywhere:**
the URL embeds a live flag code and is generated by the 72-08 rotation, then
operator-placed in the encrypted SOPS file.

## The comment rewrite (the load-bearing part)

Two comments asserted the OPPOSITE of what the file now configures. Both were rewritten,
because under fail-closed the old rationale inverts — the "brief un-guarded window" while
the sidecar loads its models becomes a brief fully-BLOCKED window.

**(a) The guardrails sidecar header** said the sidecar is safe to leave non-essential
because `MESHTK_GUARDRAIL_FAILMODE=open` "degrades to un-guarded rather than blocking."
Now: still non-essential (a crash-looping model load must not take mosquitto, the meshtk
proxy and nginx down with it), but explicit that guarded chat REFUSES while it is
unavailable, and that meshtk answers with an in-persona degradation line.

**(b) The `depends_on` rationale** justified `condition = "START"` by appealing to
fail-open. **`START` is KEPT**, with the real post-flip trade recorded:

> HEALTHY would let a permanently sick sidecar stop the ghosts container from starting AT
> ALL. That kills nodeinfo beacons and position updates too, so the ghosts vanish from the
> map entirely — a total outage in exchange for a partial one. With START, only guarded
> chat degrades.

The comment also notes the window is bounded (the sidecar's `health_check` declares
`start_period = 90`) and that a sustained outage raises the new alarm, and records that
**the design spec's C4 claim that this already read `HEALTHY` was inaccurate — it has
always been `START`.**

## Deviations from Plan

Three deviations, all in the plan's own verification one-liners rather than the work.

**1. [Plan defect - verify regex] Task 1's `grep` expects two spaces before `=`**

The command greps for `value  = "closed"`. Canonical HCL alignment inside that block is
`name  = ...` / `value = ...` — ONE space, exactly as the pre-existing `value = "open"`
line was formatted. The command can therefore never match, and printing `service.hcl OK`
would require *mis*-formatted HCL. Not "fixed" (editing the plan post-hoc hides the
defect); every prose acceptance criterion was verified individually instead:

| Criterion | Result |
|-----------|--------|
| `MESHTK_GUARDRAIL_FAILMODE` occurrences | 1 |
| its value | `closed` |
| `MESHTK_RICKY_FALLBACK_URL` occurrences | 1 |
| `mqtt/ricky-fallback-url` valueFrom | 1 |
| `condition      = "START"` occurrences | 2 (unchanged) |
| `degrades to un-guarded` occurrences | 0 |

**2. [Rule 3 - Blocking] Task 2's comment collided with its own verify command**

The action says to comment the new key; the verify command requires `ricky-fallback-url`
to appear exactly once in `site.hcl`. A comment naming the key literally makes that 2.
Resolved by writing the comment to describe the key without repeating the token, so the
verify command passes verbatim (`secret key declared, no live code present`) with the
explanatory comment intact.

**3. [Rule 3 - Blocking] Same collision on `run-mqtt-ghosts` in Task 3**

Task 3 requires `grep -c 'run-mqtt-ghosts' site.hcl` to equal 1. The Task 2 comment
mentioned the container by exact name, making it 2. Reworded to "the mqtt ghosts
container" — zero information loss, because the exact container name is documented where
it is load-bearing (`service.hcl`, which is where the `run-mqtt-ghosts` vs `ghosts`
distinction actually matters). Count is now 1, and the criterion's real intent was
verified independently: `log_group_names` still contains only `auth`/`gpx`/`human`.

**Auto-fixed:** one HCL alignment miss of my own — adding
`guardrail_outages_per_5min` (26 chars) to the `thresholds` map re-widened the alignment
column for the three existing keys. Fixed by hand rather than by running the formatter,
which would have swept 9 unrelated pre-existing drift files into the diff.

**W7 note — the reviewer's first correction was itself withdrawn, correctly.** The initial

superseded rationale** ("The old rationale here (\"meshtk fail-opens, …\") no longer
holds: …"). A bare negative grep cannot distinguish a stale claim from quoted history, and
enforcing it would have forced deletion of the sentence that explains what changed. The
plan now records that reasoning inline so the trap is not re-set later.

**W3 verified empirically**, since "this assertion cannot fail" is exactly the claim that

**Fifth correction, self-initiated (flag for reversal if unwanted):** verification item 3
